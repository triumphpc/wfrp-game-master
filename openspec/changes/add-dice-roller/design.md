## Context

The repository (`wfrp-game-master`) is a WFRP 4e game-master toolkit containing rules references (`rules/dict/`), character sheets (`characters/`), session logs (`history/`), and a RAG plugin for rule lookup (`openspec/specs/wfrp-rag-plugin/`). It has no web-facing UI and no build tooling (`no package.json`). The repo is hosted on GitHub at `triumphpc/wfrp-game-master` with GitHub Pages not yet configured.

WFRP 4e uses exactly two dice types: **d100** (for skill checks, crit/fumble tables, magic-error tables) and **d10** (for damage, initiative, scatter distance, bleed, and various tables). Polyhedral sets (d4/d6/d8/d12/d20) are not used. A d100 roll is physically two d10s — a "tens" die (00/10/…/90) and a "units" die (0–9).

The GM workflow (per `AGENTS.md`) involves: rolling d100 against a target (skill or characteristic), computing Success Levels as `(target − roll) / 10`, detecting guaranteed success (01–05) / failure (96–00), handling doubles (critical on success, fumble on fail), deriving hit location from the reversed roll, rolling `Nd10 + X` for damage with weapon-quality modifiers, and logging results to session history files in Markdown.

## Goals / Non-Goals

**Goals:**
- Deliver a single self-contained `docs/index.html` (~40KB) with all HTML, CSS, and JS inline — zero build step, zero runtime dependencies (except optional Google Fonts CDN).
- Deploy via GitHub Pages from the `/docs` folder on `main` — `git push` = deploy.
- Render d100 and d10 as clickable CSS 3D cubes that animate on roll.
- Implement WFRP 4e roll-under resolution: target + modifier (±30 cap) → d100 → success/fail + SL + crit/fumble + hit location.
- Implement damage rolling: `Nd10 + X` with weapon-quality die-cancellation (`-1s`/`-2s`) and exploding-10.
- Implement scatter helper: d10 direction (1–8) + 2d10 distance.
- Provide a hardcoded quick-skills reference keyed to characteristics.
- Persist roll history in `localStorage` with Markdown-table export.
- Apply a "Dark Empire grunge" visual theme matching WFRP's Old World aesthetic.
- Work on mobile (tap = roll) and desktop.

**Non-Goals:**
- No integration with `characters/`, `rules/dict/`, `history/`, or crit tables — the roller is standalone by explicit decision.
- No server, no backend, no share-links, no multi-user sync.
- No build tooling (Vite/webpack/npm) — single HTML file only.
- No three.js / physics engine — CSS 3D only.
- No polyhedral dice beyond d100 and d10 (WFRP 4e doesn't need them).
- No character-sheet import or automatic target lookup.

## Decisions

### Decision 1: Single-file HTML over Vite/framework build

**Choice**: One `docs/index.html` with all CSS and JS inline.

**Rationale**: The proposal explicitly scopes this to "just a page for me to roll dice." A single file means `git push` deploys with zero CI. Editing is direct. The file stays under ~40KB (well within one-file manageability). Frameworks add build complexity for a tool that has no routing, no state management beyond localStorage, and no component reuse.

**Alternatives considered**:
- *Vite + vanilla TS*: Better dev experience (HMR, modules, types), but adds `package.json`, `node_modules`, a build step, and a GitHub Action for deployment — overhead disproportionate to a single-page dice tool.
- *Astro/11ty*: Justified only if multiple pages (rules browser, char viewer) are planned. They aren't.

### Decision 2: d100 rendered as two CSS 3D cubes (tens + units)

**Choice**: The d100 "die" is two CSS 3D cubes side by side — a tens cube (showing 00/10/20/…/90) and a units cube (showing 0–9). Both animate together on a d100 roll.

**Rationale**: This mirrors how WFRP players physically roll d100 (two d10s). A true d10 pentagonal-trapezohedron geometry in CSS 3D would require ~500 lines of fragile custom face transforms for marginal authenticity gain. Two cubes with 6 visible faces each is ~150 lines of CSS, visually clear, and thematically honest.

**Alternatives considered**:
- *Single flat number*: Fast, but loses the "rolling dice" feel that the user explicitly requested.
- *True d10 geometry*: Fragile CSS, poor cross-browser 3D, no meaningful payoff.
- *three.js physics*: ~150KB dependency, overkill for a static-site dice roller.

### Decision 3: CSS 3D cube with 6 faces as a metaphor

**Choice**: Each cube is a standard 6-faced CSS 3D box (`transform-style: preserve-3d`, 6 faces positioned via rotateX/Y/Z + translateZ). The visible face after animation shows the rolled value. For d10, faces cycle 1–6 then 7–0 (two "rolls" of the metaphor) — practically, the cube shows one of 6 faces and the JS logic maps face → value for the full d10 range.

**Rationale**: CSS 3D cubes are well-supported (all modern browsers, including mobile Safari). The cube is a visual metaphor for "a die being rolled," not a geometric simulation. The actual random value is generated by JS `Math.random` and displayed on the settling face. This decouples visual fidelity from RNG correctness.

**Alternative considered**: *SVG die faces with CSS flip animation* — lighter weight but loses the 3D tactile feel the user wants.

### Decision 4: Roll-under resolution logic per AGENTS.md

**Choice**: Skill-check resolution follows the exact rules in `AGENTS.md`:
- Success Level (SL) on success = `(target − roll) / 10`, floored.
- SL on failure = `(roll − target) / 10`, floored.
- Guaranteed success: 01–05.
- Guaranteed failure: 96–00.
- Doubles (11, 22, …, 00): critical if the roll succeeds, fumble if it fails.
- Maximum modifier: ±30 (applied to target, not roll).
- Hit location: reverse the d100 digits (e.g., 47 → 74), look up 01–10 head / 11–20 body / … / 91–00 leg (per WFRP 4e hit-location table).

**Rationale**: These are the canonical WFRP 4e rules as documented in the repo's own `AGENTS.md` and `rules/dict/БОЙ.md`. Hardcoding them ensures the roller matches the GM's existing rule interpretations.

### Decision 5: localStorage for history (no IndexedDB)

**Choice**: Roll history stored as a JSON array in `localStorage` under key `wfrp-dice-history`. Capped at 500 entries (FIFO eviction). Each entry: `{id, timestamp, type, dice, target, modifier, result, sl, outcome, hitLocation, note}`.

**Rationale**: `localStorage` is synchronous, simple, and survives 500+ rolls easily (each entry ~200 bytes → 100KB, well under the 5MB limit). IndexedDB adds async complexity for no benefit at this scale.

### Decision 6: Hardcoded quick-skills list (no external data)

**Choice**: A JS object literal in the HTML file maps skill names to their governing characteristic (e.g., `{"Athletics": "S", "Charm": "WP", ...}`). Clicking a skill pre-fills the skill-check target input (empty by default — user enters their character's value) and displays the characteristic as a hint.

**Rationale**: The user explicitly excluded integration with `characters/` or `rules/`. A hardcoded list of the ~20 basic WFRP 4e skills is ~1KB of data, requires no I/O, and serves as a reference card. Advanced/specialized skills are omitted to keep the list scannable.

### Decision 7: GitHub Pages via /docs folder (no Action)

**Choice**: Configure GitHub Pages in repo settings → Source: `main` branch / `/docs` folder. No `.github/workflows/` file.

**Rationale**: No build step means no CI needed. The `/docs` folder is GitHub's native Pages source. One-time UI configuration, then every push to `main` auto-deploys.

**Alternative considered**: *GitHub Action with cache* — only justified if a build step existed. It doesn't.

## Risks / Trade-offs

- **[CSS 3D browser variance]** → Mitigation: test on Chrome, Firefox, Safari (desktop + iOS). Use `transform-style: preserve-3d` with `-webkit-` prefixes. Provide a `@media (prefers-reduced-motion)` fallback that skips animation and shows the result instantly.
- **[Single-file editability at scale]** → At ~800–1200 lines the file becomes harder to navigate. Mitigation: clear section comments (`<!-- ===== DICE LOGIC ===== -->`), consistent ordering (HTML → CSS → JS). If it grows beyond 2000 lines, reconsider extraction — but that's out of scope for this change.
- **[Google Fonts CDN dependency]** → If CDN is blocked, Cinzel won't load. Mitigation: `font-family: 'Cinzel', 'Trajan Pro', 'Times New Roman', serif` fallback chain. The page remains fully functional without the accent font.
- **[localStorage quota on shared devices]** → 500-entry cap with FIFO eviction prevents unbounded growth. If quota is exceeded, oldest entries are dropped silently. Mitigation: wrap `setItem` in try/catch and show a non-blocking toast on failure.
- **[No offline PWA]** → The page works offline only if cached by the browser. Not a goal for this change, but could be added later with a service worker (out of scope).
- **[Hit-location table accuracy]** → The reversed-digit hit-location logic must match WFRP 4e exactly (01–10 head, 11–20 r.arm, 21–30 body, 31–55 l.arm, 56–80 body, 81–90 r.leg, 91–00 l.leg). Mitigation: cross-check against `rules/dict/БОЙ.md` during implementation and add the table as a comment in the JS.
